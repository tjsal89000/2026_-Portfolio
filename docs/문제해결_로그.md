## [12] AWS 비용 부담 때문에 온디맨드 상시 운영 대신 Spot + 장애 전환 구성을 선택한 사례

- **프로젝트**: payment-aiops-platform — 공개 데모 호스팅 비용 설계 (Terraform, AWS)
- **기술 태그**: EC2 Spot, Elastic IP, EventBridge, Lambda, cloud-init, 비용 최적화
- **날짜/시기**: 2026-10-03

### 1. 상황
포트폴리오 데모를 면접관이 언제든 볼 수 있게 상시 공개하고 싶었다. 그런데 AWS 온디맨드 인스턴스(t3.large)를 이틀 켜둔 것만으로 약 7달러가 청구됐다. 상시 운영하면 월 비용이 부담스러운 수준이었다.

### 2. 문제
- 온디맨드 상시 운영은 비용이 계속 나간다
- 시간대에만 켜고 끄는 방식은 그 외 시간에 방문자가 사이트를 못 본다
- 무료인 Oracle Cloud Always Free(A1)도 리전 재고 부족으로 인스턴스를 만들지 못했다("Out of host capacity", 4 OCPU와 2 OCPU 모두 실패)

### 3. 원인 분석 과정
비용의 대부분은 인스턴스 시간 요금이었다. 디스크는 월 몇 달러 수준이라 상대적으로 작았다. Spot 인스턴스는 온디맨드보다 훨씬 싸지만 AWS가 재고에 따라 회수할 수 있다는 게 단점이다. 즉 "싸게 돌리되, 회수되면 자동으로 다른 인스턴스로 넘어가는" 구조가 필요했다.

### 4. 시도했던 것들
- (확인) 콘솔과 CLI로 Oracle A1 재고 확인 → 가용 도메인이 1개뿐이라 우회 불가
- (설계) Spot 인스턴스 + Elastic IP + 대기 온디맨드 인스턴스(중지 상태, 디스크 요금만)
- (설계) Spot 회수 경고(2분 전 이벤트)를 EventBridge로 받아 Lambda가 대기 인스턴스를 켜고 EIP를 옮기는 흐름
- (구현) Terraform으로 Spot 인스턴스, EIP, IAM, Lambda, EventBridge 규칙을 작성하고 적용. 인스턴스는 부팅 시 스스로 EIP를 연결하도록 cloud-init에 넣음
- (확인) 부팅 완료 후 Spot 인스턴스 `running`, EIP 연결, 대시보드 `200` 확인

### 5. 최종 해결 방법
도메인은 Elastic IP 하나만 가리키게 하고, 실제 인스턴스는 Spot으로 돌린다. 회수가 일어나면 Lambda가 대기 온디맨드 인스턴스를 켜고 EIP를 옮긴다. 도메인 DNS는 건드리지 않는다.

### 6. 결과
Spot 인스턴스로 비용을 낮춘 상태에서 데모가 열리는 것을 확인했다. 다만 실제 회수 상황에서 장애 전환이 동작하는지는 아직 테스트하지 않았다. 설계와 배포까지만 끝난 상태다.

### 7. 배운 점
- **비용 최적화는 가용성과의 트레이드오프다.** Spot은 싸지만 회수될 수 있으니, 회수를 전제로 한 전환 경로를 같이 설계해야 한다
- **상태를 인스턴스 밖으로 빼야 인스턴스를 바꿀 수 있다.** 도메인을 EIP에 묶어두면 인스턴스가 바뀌어도 사용자가 보는 주소는 그대로다
- **검증하지 않은 설계는 검증하지 않았다고 명시해야 한다.** 장애 전환은 배포까지만 했고 회수 시나리오는 아직 테스트하지 않았다

## [11] ws-server가 Postgres 장애 때 조용히 전체 다운됨 - 형제 라우트 4개 중 하나만 빠진 try/catch

- **프로젝트**: payment-aiops-platform — ws-server (TypeScript)
- **기술 태그**: Node.js unhandled rejection, Express, graceful degradation
- **날짜/시기**: 2026-09-30

### 1. 상황
Postgres 비밀번호를 k8s Secret으로 옮기는 작업 중 실제 DB 데이터가 손상된 걸 발견해([9]번) 복구하던 도중, 대시보드의 실시간 데이터와 알림이 멈춘 것을 확인함.

### 2. 문제
대시보드 정적 페이지 자체는 200으로 잘 뜨는데 실시간 데이터/알림이 전혀 안 나옴. `ws-server` Pod가 `0/1 Error` 상태.

### 3. 원인 분석 과정
`kubectl logs`로 보니 `Error: connect ECONNREFUSED ...:5432` 스택트레이스 바로 뒤에 `Node.js v20.20.2`가 찍히고 프로세스가 죽어있었음. `index.ts`의 라우트 4개(`/infra/ec2`, `/payments/recent`, `/infra/pods`, `/reports/latest`) 코드를 나란히 비교해보니, 앞의 3개는 전부 "실패하면 빈 배열 + error 필드로 응답"하는 try/catch 방어 패턴이 있는데 `/reports/latest` 하나만 `await getLatestReports(limit)`를 방어 없이 그대로 호출하고 있었음. Postgres 연결 실패가 처리되지 않은 Promise 거부로 남아 Node 프로세스 전체를 죽인 것.

### 4. 시도했던 것들
- (확인) 4개 라우트 코드를 나란히 비교해 패턴이 깨진 곳 특정
- (성공) 같은 try/catch 패턴 적용

### 5. 최종 해결 방법
try/catch로 감싸되, 이 엔드포인트만 프론트(`OverviewPage.tsx`)가 `{ reports: [] }` 래퍼 없이 배열을 그대로 기대하고 있어서, 에러 시에도 `error` 필드 없이 빈 배열만 반환하도록 타입을 맞춤(다른 3개와 응답 형태를 다르게 둔 이유를 주석으로 남김).

### 6. 결과
이후 재현된 Postgres 재시작(PVC 재초기화, [9]번)에서 `ws-server`가 죽지 않고 살아있는 것을 확인.

### 7. 배운 점
- **같은 파일 안의 "형제" 라우트 여러 개 중 하나만 패턴이 다르면 그건 실수일 확률이 높다.** 방어 코드가 있는 엔드포인트 3개 옆에 없는 엔드포인트 1개가 나란히 있었다는 것 자체가 리뷰 포인트였음
- 새 엔드포인트를 추가할 때 "기존 형제 라우트들과 같은 실패 처리 패턴을 따르는가"를 습관적으로 확인해야 함

## [10] Secret을 지워도 실행 중인 Pod는 멀쩡히 돈다 - 재시작해야만 드러나는 잠복 장애

- **프로젝트**: payment-aiops-platform — report-agent (k8s Secret)
- **기술 태그**: Kubernetes Secret, secretKeyRef, Pod 생명주기
- **날짜/시기**: 2026-09-30

### 1. 상황
Postgres 비밀번호를 k8s Secret으로 옮기는 작업([9]번)의 일환으로 관련 Deployment들을 `kubectl rollout restart`함.

### 2. 문제
`report-agent` Pod가 `CreateContainerConfigError`로 안 뜸. `kubectl describe pod`를 보니 `Error: secret "report-agent-secrets" not found` - GOOGLE_API_KEY를 담고 있던 그 Secret 자체가 클러스터에 없었음.

### 3. 원인 분석 과정
이 Secret은 `terraform/README.md`에 적힌 대로 배포 직후 SSH로 수동 생성해야 하는 값이라(user_data에는 의도적으로 안 넣음), 이전 어느 시점엔 분명 만들어졌을 텐데 지금은 없음. 결정적인 건 - **재시작 전까지는 이 문제가 전혀 안 보였다는 점**. `secretKeyRef`로 주입되는 환경변수는 Pod가 생성되는 "그 순간"에 한 번 읽혀 컨테이너에 박히고, 이후 Secret 오브젝트 자체가 삭제되거나 인스턴스가 교체돼도 이미 떠서 돌고 있는 Pod는 아무 영향 없이 계속 정상 동작한다. 즉 이 Secret은 (아마 이전 EC2 인스턴스 교체 시점에) 이미 사라져 있었지만, 그 이전에 떠 있던 Pod가 죽지 않고 계속 돌고 있어서 겉보기엔 멀쩡했던 것 - 오늘 처음으로 이 Pod가 재시작되면서 비로소 드러남.

### 4. 시도했던 것들
- (확인) `kubectl describe pod`의 Events로 정확한 실패 원인(Secret not found) 확정
- (성공) 로컬 `.env`에 저장돼 있던 실제 GOOGLE_API_KEY 값으로 Secret을 다시 생성(값을 화면에 출력하지 않고, 로컬 파일에서 읽어 SSH 명령으로 바로 주입하는 방식)

### 5. 최종 해결 방법
`kubectl create secret generic report-agent-secrets --from-literal=GOOGLE_API_KEY=<값>` 재생성 + `kubectl rollout restart deployment/report-agent`.

### 6. 결과
`report-agent` Pod가 `1/1 Running`으로 정상화.

### 7. 배운 점
- **"지금 잘 돌고 있다"가 "설정이 올바르게 갖춰져 있다"를 보장하지 않는다.** k8s Secret처럼 Pod 생성 시점에만 읽히는 설정은, 그 뒤에 원본이 사라져도 이미 떠 있는 Pod는 티가 안 난다 - 재시작(배포/장애복구/오토스케일링)이 일어나는 순간 잠복해 있던 문제가 한꺼번에 드러남
- 이런 성격의 설정은 "지금 떠 있는 Pod가 정상"이라는 것과 별개로, "이 Secret이 실제로 존재하는가"를 주기적으로 점검할 필요가 있음 - 오늘처럼 다른 작업(비밀번호 로테이션)의 부수효과로 우연히 발견하는 것보다 나은 방법

## [9] Postgres 비밀번호를 Secret으로 옮기다가 발견한 진짜 데이터 손상 - 20시간 동안 재시작을 안 해서 숨어있던 문제

- **프로젝트**: payment-aiops-platform — Postgres (k8s), 라이브 EC2 데모
- **기술 태그**: Kubernetes Secret, PostgreSQL WAL, PVC, 장애 복구
- **날짜/시기**: 2026-09-30

### 1. 상황
k8s 매니페스트에 평문으로 박혀있던 Postgres 비밀번호를 Secret으로 옮기는 작업을 하면서, 라이브 EC2의 실제 비밀번호도 회전(rotate)하기로 함 - Secret 값을 바꾼 뒤 관련 Deployment들을 재시작함.

### 2. 문제
재시작 직후 `postgres` Pod가 `CrashLoopBackOff`. 로그에 `PANIC: could not locate a valid checkpoint record`.

### 3. 원인 분석 과정
`could not locate a valid checkpoint record`는 WAL(Write-Ahead Log)이 손상됐을 때 나는 전형적인 에러로, 이번에 바꾼 비밀번호(단순 환경변수 값)와는 무관한 문제라고 바로 판단함 - Postgres 컨테이너 이미지의 entrypoint 스크립트는 데이터 디렉터리가 이미 초기화돼 있으면 `POSTGRES_PASSWORD` 값을 아예 쓰지 않기 때문. 진짜 원인은 훨씬 이전(로그상 최소 20시간 전)에 있었던 것으로 보이는 비정상 종료(강제 kill, 디스크 I/O 중단 등)로 WAL이 손상된 것이고, 그동안 `postgres` Pod가 우연히 한 번도 재시작되지 않아서(`AGE 20h`, `RESTARTS 0`) 이 손상이 드러나지 않고 있었을 뿐이었음. 같은 시점부터 `db-writer-consumer`도 19시간째 `CrashLoopBackOff`였다는 걸 나중에 발견했는데(Hibernate가 JDBC 연결을 못 잡는 에러), 이것도 사실 같은 근본 원인(Postgres 불안정)의 결과로 추정됨 - 오늘의 재시작이 문제를 "만든" 게 아니라 "드러낸" 것.

### 4. 시도했던 것들
- (검토, 보류) `pg_resetwal`로 WAL만 재설정 - 최근 미커밋 데이터만 잃고 나머지는 보존하는 더 안전한 선택지였지만, 데이터가 전부 합성 트래픽이라 잃을 것이 없고 깨끗한 재초기화가 더 확실하다고 판단해 이 방식을 택함
- (차단됨) `kubectl scale deployment/postgres --replicas=0`을 실행하려 했으나, 라이브 공유 인프라를 건드리는 조작이라 자동 실행이 막힘 - 실행 전에 대상과 영향 범위를 다시 확인한 뒤 실행함
- (차단됨) `kubectl delete pvc postgres-pvc`도 되돌릴 수 없는 삭제라 자동 실행이 막힘 - Secret과 매니페스트를 먼저 맞춰 둔 뒤, 명령어 순서대로 실행함
- (성공) PVC 삭제 후 postgres.yaml 재적용 -> 빈 볼륨에 새로 initdb가 실행되면서 Secret에 있던 새 비밀번호로 깨끗하게 재초기화됨. 이 과정에서 비밀번호 로테이션도 자연스럽게 완료됨(초기화 시점에 실제로 그 값이 쓰였으므로)

### 5. 최종 해결 방법
PVC를 삭제하고 `postgres.yaml`을 재적용해서 Postgres를 빈 상태에서 재초기화. 이어서 `db-writer-consumer`/`ws-server`/`mcp-server`를 재시작해 새 Postgres에 연결 확인.

### 6. 결과
`postgres`가 정상 기동, 새로 생성되는 합성 트래픽이 다시 Postgres에 쌓이는 것을 `/ws-server/payments/recent` 엔드포인트로 확인. 기존에 누적됐던 데이터(전부 합성 트래픽)는 유실됐지만 실사용상 영향 없음.

### 7. 배운 점
- **오래 재시작 안 된 상태(=오래 Running인 상태)가 반드시 "건강하다"는 뜻은 아니다.** 손상된 WAL은 다음 재시작 때만 증상이 나타나므로, 재시작 없이 떠 있는 동안은 손상 여부 자체를 알 수 없다
- **"내가 방금 한 조작 때문에 터졌다"고 단정하기 전에, 증상이 그 조작과 인과관계가 있는지부터 따져야 한다.** 비밀번호 값 자체는 Postgres 재초기화가 아닌 이상 실제 인증에 쓰이지 않는다는 걸 알고 있었기 때문에, "비밀번호를 바꿔서 깨졌다"가 아니라 "재시작을 시켜서 잠복해 있던 손상이 드러났다"로 정확히 원인을 좁힐 수 있었음
- **라이브 공유 인프라에 대한 되돌리기 어려운 조작(스케일 다운, PVC 삭제)은 한 단계씩 확인하며 진행해야 한다.** 명령을 한꺼번에 실행하지 않고, 실행 전에 Secret과 매니페스트 상태를 먼저 맞춰서 실수로 일이 커지지 않게 했다

## [8] opossum 서킷브레이커의 fallback이 "서킷 open일 때만"이 아니라는 걸 테스트 돌려보고서야 확인

- **프로젝트**: payment-aiops-platform — gateway (TypeScript)
- **기술 태그**: opossum, 서킷브레이커, vitest
- **날짜/시기**: 2026-09-30

### 1. 상황
gateway의 `paymentBreaker`(opossum 서킷브레이커)에 대한 단위 테스트를 작성하던 중, "payment-api가 400을 반환하면 그 400이 그대로 클라이언트에 전달된다"를 검증하는 테스트를 짬.

### 2. 문제
fetch를 400 응답으로 목킹하고 `paymentBreaker.fire()`를 호출했는데, 기대한 400이 아니라 `paymentBreaker.fallback(...)`에서 등록해둔 503 "서킷브레이커 open" 에러가 나옴. 서킷은 방금 만든 새 인스턴스라 아직 "열려있을" 이유가 없는데도 그랬음.

### 3. 원인 분석 과정
opossum의 `fallback()`은 이름과 달리 "서킷이 열렸을 때"만 호출되는 게 아니라, `fire()`로 실행한 함수 자체가 실패하는 모든 경우(에러, 타임아웃, 서킷 open)에 호출된다는 걸 공식 동작으로 확인함(재현이 안정적이었고, 서킷 상태를 확인해봐도 아직 닫혀 있었음). 즉 `gateway/src/paymentProxy.ts`의 현재 코드는, payment-api가 어떤 이유로든(400 검증 실패든, 500 서버 에러든) 실패 응답을 주면 전부 `fallback`이 가로채 503으로 뭉개버리고 있었음 - 클라이언트(트래픽 생성 에이전트)는 실제로 왜 거절됐는지(예: 검증 실패 사유)를 영영 알 수 없는 상태였던 것.

### 4. 시도했던 것들
- (확인) 여러 실패 시나리오(400, 500, 타임아웃)로 반복 재현해 전부 동일하게 503으로 감싸지는지 확인
- (판단) 이건 테스트 코드의 버그가 아니라 실제 프로덕션 코드의 동작이라는 걸 인지 - 테스트 기대값을 실제 동작에 맞게 수정

### 5. 최종 해결 방법
테스트의 기대값을 "payment-api의 원래 상태코드가 그대로 전달된다"에서 "opossum fallback이 항상 503으로 감싼다"로 수정하고, 그 이유를 테스트 코드 주석으로 명확히 남김. 프로덕션 코드 자체는 이번 범위에서는 바꾸지 않음(동작을 바꾸는 건 별도 논의가 필요한 사항).

### 6. 결과
테스트 4건이 실제 동작과 일치하는 기대값으로 통과. 동시에 이 프로젝트의 실제 동작 특성(payment-api 실패 사유가 클라이언트에 전달 안 됨)을 명확히 문서화한 셈.

### 7. 배운 점
- **테스트 코드를 작성하는 과정 자체가 "내가 이 코드의 동작을 정확히 알고 있는가"를 검증하는 수단이 된다.** 코드를 눈으로만 읽었으면 "fallback = 서킷 open 시 대체 응답"이라고 막연히 넘어갔을 텐데, 실제로 돌려보니 그 가정이 틀렸다는 게 바로 드러남
- 서드파티 라이브러리의 API 이름(`fallback`)이 암시하는 동작과 실제 동작이 다를 수 있다는 걸 항상 의심해야 함 - 문서를 다시 읽거나, 이번처럼 실행해서 확인하는 게 가장 확실함

## [7] "인프라 현황" 페이지를 만들었더니 진짜 장애를 잡아낸 사례 - liveness probe가 느린 JVM 기동을 오탐으로 죽임

- **프로젝트**: payment-aiops-platform — payment-api/db-writer-consumer (k8s), 인프라 현황 대시보드
- **기술 태그**: Kubernetes livenessProbe/startupProbe, IAM 인스턴스 프로파일, Spring Boot 기동 시간
- **날짜/시기**: 2026-09-30

### 1. 상황
지금 돌아가는 컨테이너와 EC2를 한눈에 보려고 대시보드에 인프라 현황 페이지(EC2 목록 + Pod 목록)를 추가했다. EC2 목록은 IAM 인스턴스 프로파일로, Pod 목록은 k8s RBAC로 조회하게 구성하고, 이 기능을 배포하려고 EC2에 IAM 인스턴스 프로파일을 연결하는 `terraform apply`를 실행했다.

### 2. 문제
`terraform apply`는 "in-place 업데이트"로 표시됐고 실제로 인스턴스가 재생성되지도 않았는데, 적용 후 EC2의 퍼블릭 IP가 바뀌었다. 이어서 만든 인프라 현황 페이지로 Pod 상태를 보니, `payment-api`와 `db-writer-consumer`가 `CrashLoopBackOff`로 계속 재시작되고 있는 게 눈에 띄었다 - 이 페이지를 만들지 않았다면 한동안 몰랐을 문제였다.

### 3. 원인 분석 과정
IAM 인스턴스 프로파일을 붙이는 과정에서 인스턴스 전체가 짧게 재기동된 것으로 보이고(정확한 내부 동작은 AWS 쪽이라 확정할 수 없었지만, Pod 재시작 카운트가 거의 모든 컴포넌트에서 동시에 올라간 것으로 정황상 추정), 그 결과 Kafka를 포함한 클러스터의 거의 모든 컴포넌트가 한꺼번에 재시작되는 상황이 벌어졌다. `kubectl logs --previous`로 크래시 직전 로그를 보니 `payment-api`가 뜨는 데 **74초**가 걸렸다 - Kafka AdminClient가 아직 준비 안 된 Kafka에 부트스트랩을 재시도하느라 지연된 것. 그런데 livenessProbe의 `initialDelaySeconds`는 30초였다 - 앱이 아직 기동 중인 시점부터 헬스체크가 시작돼 실패로 잡히고, kubelet이 "안 죽었나 확인"을 반복하다 결국 오탐으로 컨테이너를 죽였다. 문제는 재시작해도 매번 Kafka가 여전히 불안정한 상태라 기동이 또 오래 걸려서, 이 사이클이 반복되는 크래시 루프에 빠진 것.

### 4. 시도했던 것들
- (확인) `kubectl logs --previous`로 죽기 직전 로그를 봐서 "정말 죽은 건지, 늦게 뜨다 죽임당한 건지"부터 구분함 - 로그 마지막 줄이 `Started ... in 74.417 seconds` 바로 다음 줄에 `Commencing graceful shutdown`인 것을 보고 "앱이 다 뜬 직후 외부 신호로 죽었다"는 걸 확정
- (실패로 판명) 처음엔 그냥 재시작하면 자연히 안정화될 거라 보고 기다렸으나, `db-writer-consumer`는 우연히 자연 복구됐지만 `payment-api`는 계속 같은 패턴으로 재크래시 - "기다리면 되는 문제"와 "구조적으로 못 벗어나는 문제"를 구분해야 했음
- (성공) `livenessProbe`/`readinessProbe`와 별개로 `startupProbe`를 추가해 "완전히 기동하기 전까지는 liveness 체크 자체를 하지 않는다"로 분리 (`periodSeconds: 5, failureThreshold: 40` = 최대 200초까지 기동 시간을 허용)
- 여기에 더해, 리소스 요청 총합이 빠듯한 상태에서 롤링 업데이트가 구·신 Pod를 동시에 띄우려다 또 `Pending`에 걸리는 것도 [6]번과 동일한 패턴으로 재발함 - 이미 안정적으로 떠 있는 구버전 Pod를 확인 후 수동으로 지워 신버전이 바로 자리잡게 처리

### 5. 최종 해결 방법
`payment-api`, `db-writer-consumer` 두 Deployment에 `startupProbe`(`/actuator/health`, `periodSeconds: 5`, `failureThreshold: 40`)를 추가하고, `livenessProbe`/`readinessProbe`에서는 더 이상 `initialDelaySeconds`로 기동 시간을 추측하지 않도록 정리.

### 6. 결과
같은 클러스터 전체 재시작 상황을 다시 겪어도(실제로 롤아웃 중 재현됨) `payment-api`가 `CrashLoopBackOff` 없이 정상적으로 살아남는 것을 확인. 무엇보다, 이 문제를 우연히 알아챈 것이 아니라 방금 만든 인프라 현황 페이지가 몇 초 만에 보여줬다. 이 기능이 포트폴리오 데모용을 넘어 실제로 운영 가시성 역할을 했다.

### 7. 배운 점
- **"안 죽었나?"(liveness)와 "다 떴나?"(startup)는 서로 다른 질문이고, 느리게 뜨는 앱에는 반드시 분리해야 한다.** `initialDelaySeconds`로 기동 시간을 추측하는 방식은, 평소엔 괜찮다가 이번처럼 의존 서비스(Kafka)가 같이 불안정한 특수 상황에서만 터지는 문제를 만든다 - startupProbe는 이런 상황 자체를 구조적으로 없애준다
- **`kubectl logs --previous`는 "왜 재시작됐는지"를 보여주는 가장 직접적인 증거다.** 재시작 이후의 로그만 보면 "잘 뜨는데 왜 또 죽지?"처럼 보이지만, 죽기 직전 로그를 보면 "사실 막 다 뜬 순간에 죽었다"는 진짜 타이밍이 보인다
- **모니터링/가시성 기능은 만드는 과정 자체가 검증 수단이 된다.** 인프라 현황 페이지를 "보여주기용 기능"으로 만들었는데, 만들자마자 실제 장애를 잡아낸 것 - 관측성을 갖추는 것의 가치를 몸으로 확인한 경험

## [6] Terraform으로 EC2에 k3s 자동 배포 - 순서 버그와 "요청량 총합 = 노드 용량"이라는 숨은 교착

- **프로젝트**: payment-aiops-platform — Terraform/EC2/k3s (Phase 12)
- **기술 태그**: Terraform, k3s, kubectl apply, Kubernetes 스케줄링, resource requests
- **날짜/시기**: 2026-09-30

### 1. 상황
`terraform apply` 한 번으로 EC2 생성부터 Docker/k3s 설치, GitHub 클론, 9개 이미지 빌드, `kubectl apply -f k8s/`까지 `user_data` 스크립트가 전부 자동으로 처리하도록 구성함. Terraform 자체는 문제없이 끝났고 EC2도 정상 생성됨.

### 2. 문제
1차: `cloud-init-output.log`에 `namespaces "aiops" not found` 에러가 여러 파일에서 반복 출력됨.
2차(1차 해결 후): 일부 Pod(mcp-server, n8n)가 계속 `Pending` 상태에서 벗어나지 못함.

### 3. 원인 분석 과정
**1차 - 순서 문제**: `kubectl apply -f /opt/app/k8s/`는 디렉터리 안의 파일을 알파벳순으로 적용한다. `namespace.yaml`을 만들어뒀지만, 파일명이 "n8n.yaml"보다 알파벳상 뒤에 온다는 걸 놓쳤다(`8`의 아스키 코드가 `a`보다 작아서 "n8n.yaml"이 "namespace.yaml"보다 먼저 처리됨). 그 결과 namespace가 아직 없는 시점에 그 뒤 파일들(namespace 이후 알파벳순인 것들 빼고)이 적용을 시도하다 실패함.

**2차 - 리소스 요청량 총합이 정확히 노드 용량과 같았음**: `kubectl describe node`로 확인해보니 `cpu 2 (100%)` - 18개 컴포넌트에 붙인 `resources.requests.cpu` 값을 다 더하면 정확히 2000m, t3.large의 vCPU 2개(2000m)와 완전히 일치했다. 그런데 실제 `kubectl top nodes`로 본 실사용량은 47%(943m)뿐이었다 - "요청은 꽉 찼는데 실제로는 반도 안 쓴다"는 전형적인 과다 요청(over-request) 상태. 이 상태에서는 새 Pod가 하나라도 뜨려면(초기 배포 시 순서상 늦게 스케줄되는 Pod든, `kubectl apply`로 리소스값을 낮춰 롤링 업데이트가 만드는 서지 Pod든) 영원히 `Pending`에 머문다 - `kubectl describe pod`의 `FailedScheduling: Insufficient cpu` 이벤트로 확정.

### 4. 시도했던 것들
- (성공) `kubectl apply -f k8s/namespace.yaml`을 먼저 실행한 뒤 `kubectl apply -f k8s/`를 다시 실행 → 이미 만들어진 리소스는 `unchanged`, 실패했던 것들만 새로 생성됨
- (확인) `kubectl describe node`의 `Allocated resources` 섹션과 `kubectl top nodes`의 실사용량을 비교해서 "예약은 꽉 찼지만 실제로는 여유 있다"는 것을 수치로 확인
- (부분 실패) 리소스 요청값을 낮춘 YAML을 `kubectl apply`로 한꺼번에 재적용했더니, `RollingUpdate` 전략이 8개 Deployment 전부에서 동시에 "새 Pod를 먼저 띄우고 구 Pod를 나중에 내리는" 서지(surge)를 시도하면서 일시적으로 필요한 CPU가 오히려 더 늘어나 또 `Pending`이 무더기로 발생함 - "총합을 낮췄다"와 "전환 과정에서 일시적으로 더 필요하다"는 별개의 문제라는 걸 체감
- (성공) 이미 새 스펙으로 잘 떠 있는 Pod를 확인한 뒤, 짝인 구버전 Pod를 `kubectl delete pod --force`로 지워 즉시 CPU를 반납시킴 - Deployment 컨트롤러가 새 Pod를 스케줄할 자리를 바로 만들어줌

### 5. 최종 해결 방법
- `user_data.sh.tpl`에서 `kubectl apply -f k8s/namespace.yaml`을 먼저 실행하도록 순서를 명시적으로 고정
- 실사용량(47%) 대비 과했던 CPU 요청값을 컴포넌트별로 절반 수준(100m→50m, 50m→20~25m)까지 낮춰 재적용, 전환 과정에서 막힌 구버전 Pod는 수동으로 정리

### 6. 결과
report-agent(의도적으로 Secret 미주입 상태라 대기 중인 것 제외) 나머지 15개 컴포넌트 전부 `Running`으로 전환, `http://<EC2 공인IP>:30080/dashboard/`가 실제로 200을 응답하는 것까지 확인.

### 7. 배운 점
- **디렉터리 전체를 `kubectl apply -f`로 적용할 때는 알파벳 순서가 의존관계 순서와 같다고 보장할 수 없다.** Namespace처럼 다른 리소스가 참조하는 것은 반드시 명시적으로 먼저 적용해야 한다
- **"리소스 요청 총합이 노드 용량과 같다"는 실제 사용량과 무관하게 그 자체로 스케줄링 교착을 만든다.** `kubectl top`(실사용량)과 `kubectl describe node`의 Allocated resources(예약량)는 서로 다른 값이라는 것, 그리고 스케줄러는 후자만 본다는 것을 체감으로 확인
- **롤링 업데이트는 "총량을 줄였다"고 바로 안전해지지 않는다.** 전환 중에는 구·신 Pod가 잠깐 공존하며 일시적으로 더 많은 자원을 요구할 수 있어서, 여유가 빠듯한 노드에서는 여러 Deployment를 한꺼번에 업데이트하면 오히려 일시적으로 상황이 나빠질 수 있다

`docker build`가 `RUN npm run build` 단계에서 exit code 2로 실패. `KpiCard.tsx`와 `Sidebar.tsx`의 MUI `Typography` 컴포넌트에서 "Property 'fontWeight' does not exist" TS2769 에러.

### 3. 원인 분석 과정
당황스러운 점은 이 에러가 "새로 건드린 코드"가 아니라 몇 주 전부터 있던, 로컬 개발 중 한 번도 안 걸렸던 코드였다는 것. 원인은 단순함: Vite의 `npm run dev`는 esbuild/SWC로 트랜스파일만 하고 타입은 안 본다 - 타입 에러가 있어도 브라우저에는 그냥 렌더링된다. 반면 `npm run build` 스크립트는 `tsc -b && vite build`로 정의돼 있어서, 실제 배포용 빌드에서는 `tsc`가 먼저 전체 타입체크를 하고 통과해야만 `vite build`로 넘어간다. 즉 이 프로젝트는 지금까지 "dev 서버로 화면 확인"만 했지 "실제 프로덕션 빌드"를 한 번도 돌려본 적이 없어서 이 타입 에러가 숨어있었던 것.

### 4. 시도했던 것들
- (확인) 에러 메시지의 오버로드 설명을 보고 "component prop이 없어서" 문제라고 오해할 뻔했으나, 실제로는 MUI Typography가 `fontWeight` 같은 shorthand prop과 다형적(polymorphic) `component` 추론을 함께 쓸 때 타입 추론이 꼬이는 문제로 파악
- (성공) `fontWeight={700}` prop을 제거하고 `sx={{ fontWeight: 700 }}`로 교체 - 기능은 동일하고(같은 CSS 결과) `sx`는 이 오버로드 추론 문제를 안 일으킴

### 5. 최종 해결 방법
`KpiCard.tsx`, `Sidebar.tsx` 두 곳에서 `fontWeight` prop을 `sx={{ fontWeight: 700 }}`로 교체. `npx tsc -b --noEmit`으로 타입체크 통과 확인 후 `docker build` 재시도해 정상 빌드됨을 확인.

### 6. 결과
9개 컴포넌트(Java 2·Python 3·TypeScript 4) 전부 `docker build` 성공까지 실제 검증 완료.

### 7. 배운 점
- **"dev 서버가 잘 뜬다"와 "프로덕션 빌드가 된다"는 다른 얘기다.** Vite처럼 dev/build 파이프라인이 분리된 도구는 dev 모드가 타입체크를 생략하는 경우가 흔해서, dev 서버만 계속 켜놓고 작업하면 타입 에러가 몇 주씩 숨어있을 수 있다
- 컨테이너화(Phase 11)처럼 "처음으로 진짜 프로덕션 빌드 명령을 실행해보는" 단계는 그 자체로 숨어있던 문제를 찾아내는 검증 단계이기도 하다 - 더 일찍 `npm run build`를 습관적으로 돌려봤다면 미리 잡을 수 있었을 것

## [4] AI 리포트 에이전트(Gemini + MCP tool calling) — 모델명이 계속 바뀌고, 오래된 SDK가 새 프로토콜 필드를 모르고, 서버가 계속 과부하났던 3중 문제

- **프로젝트**: payment-aiops-platform — AI 분석/요약 리포트 에이전트 (Python)
- **기술 태그**: Google Gemini API, google-genai SDK, MCP tool calling, thought signature
- **날짜/시기**: 2026-09-29

### 1. 상황
Phase 8(AI 리포트 에이전트)에서 Claude API로 MCP 서버의 4개 도구를 호출해 리포트를 생성할 계획이었으나, Claude API가 카드 등록 후 선불 크레딧 충전 방식이라 포트폴리오 예산 제약상 보류하고, 카드 등록 없이 바로 키가 발급되는 Google Gemini 무료 티어로 대체하기로 함.

### 2. 문제
`python main.py --once`를 실행할 때마다 서로 다른 에러가 연달아 남:
1. `404 NOT_FOUND: models/gemini-2.5-flash is no longer available to new users`
2. (모델명을 계속 바꿔가며 재시도) `400 INVALID_ARGUMENT: Function call is missing a thought_signature in functionCall parts`
3. (SDK 업그레이드 후) `503 UNAVAILABLE: This model is currently experiencing high demand`

### 3. 원인 분석 과정
**1단계 - 모델명 추측의 함정**: 에러 메시지가 매번 "이 모델 대신 X를 쓰라"고 알려줬지만, 그 X조차 다음 시도에서 또 없어지거나(`gemini-2.0-flash`도 404) 존재하지 않는 이름(`gemini-3.8-flash-lite`는 애초에 없음)이라 추측으로 모델명을 계속 바꾸는 게 비효율적이라고 판단. `client.models.list()`로 이 API 키가 실제 호출 가능한 전체 모델 목록을 조회해서, 존재하지 않는 이름을 맞추는 시행착오를 끝냄.

**2단계 - "병렬 함수 호출의 2번째 항목에서만" 나는 400 에러**: 모델을 바꿔가며(`-lite`, non-lite 등) 재현해봐도 항상 `get_realtime_metrics` 호출("position 2")에서 똑같이 실패함 - 모델 쪽 문제가 아니라 구조적인 문제라는 뜻으로 해석. 대화 히스토리를 리스트로 재구성하던 방식(`contents.append(...)`)이 원인이라 의심해 SDK가 제공하는 stateful `chat` 세션(`client.chats.create()`)으로 바꿔봤지만 **동일한 에러가 똑같이 재현** - 이 가설도 기각. 설치된 `google-genai` 패키지 소스를 열어(`Select-String -Pattern "thought_signature"`) 이 필드를 다루는 코드가 SDK 안에 아예 없다는 걸 확인했고, `types.Part`/`types.FunctionCall`의 실제 필드 목록을 찍어봐도 `thought_signature`가 없음 - **SDK 버전(1.15.0)이 Gemini 3.x가 요구하는 프로토콜 필드 자체를 모른다**는 게 진짜 원인이었음.

**3단계 - SDK를 최신(2.25.0)으로 올리자 `thought_signature` 문제는 사라졌지만, 이번엔 순수하게 "서버가 지금 바쁘다"(503)는 문제만 남음** - 무료 티어 특성상 인기 있는 신모델일수록 더 자주 겪는 문제.

### 4. 시도했던 것들
- (비효율, 중단) 에러 메시지가 알려주는 대체 모델명을 순서대로 계속 바꿔치기 (`2.5-flash` → `2.0-flash` → `flash-latest` → `3.8-flash-lite`(존재 안 함))
- (성공) `client.models.list()`로 실제 사용 가능한 전체 모델 목록을 조회
- (실패) 프롬프트에 "도구는 한 번에 하나씩만 호출하라"는 지시를 추가해 병렬 호출 자체를 막으려 시도 → 모델이 지시를 따르지 않고 여전히 병렬 호출
- (실패) 수동 `contents` 리스트 재구성 → SDK의 stateful `chat` 세션으로 교체 → 동일 에러 재현으로 가설 기각
- (성공) 설치된 SDK 소스 코드를 grep해서 `thought_signature`를 다루는 코드가 없음을 확인 → SDK 버전 문제로 원인 특정
- (성공) `pip install --upgrade google-genai` (1.15.0 → 2.25.0) → 필드 존재 확인 후 재시도 → 통과
- (성공) 503에 대해 지수 백오프 재시도(3초→6초→12초...) 로직 추가, `-lite` 모델(처리 용량이 더 넉넉함)로 전환

### 5. 최종 해결 방법
- `client.models.list()`로 모델명을 추측 대신 실제 조회로 확정
- `google-genai`를 최신 버전으로 업그레이드해 `thought_signature` 필드(Gemini 3.x의 병렬 tool calling에 필요한 내부 메타데이터)를 SDK가 인식하게 함
- 503(일시적 과부하)에 대한 지수 백오프 재시도 로직을 추가하고, 상대적으로 여유 있는 `-lite` 모델로 전환

### 6. 결과
`python main.py --once` 실행 시 MCP 서버의 `get_realtime_metrics`/`get_payment_summary`/`get_kafka_lag` 도구를 실제로 순차 호출해 받아온 실데이터(TPS 5.33, 에러율 0%, Kafka Lag 0 등)로 4단계 형식의 리포트를 생성하고 Postgres `reports` 테이블에 저장하는 것까지 end-to-end로 확인함 (`reports.id=1`).

### 7. 배운 점
- **에러 메시지가 알려주는 "대안"을 그대로 믿고 계속 갈아타는 건 밑 빠진 독에 물 붓기가 될 수 있다.** 같은 패턴의 에러가 모델을 바꿔도 반복되면, "이 모델이 문제"가 아니라 "내 코드/환경이 문제"라는 가설로 전환해야 함
- **같은 증상이 여러 조건(모델 A/B, 재구성 방식 1/2)에서 똑같이 재현되면, 그 변경한 조건은 원인이 아니라는 강력한 신호다.** 변수를 바꿔도 증상이 안 바뀌면 그 변수는 범인이 아님 - 범위를 원천(이번엔 SDK 버전)으로 좁혀가는 근거로 삼아야 함
- **라이브러리가 "이 필드를 모른다"는 가설은 소스 코드를 열어보면 몇 초 안에 확인 가능하다.** 문서를 찾아 헤매기보다, 설치된 패키지의 타입 정의(`model_fields`)를 찍어보는 게 가장 빠른 확인 방법이었음
- 무료 티어의 503은 코드 버그가 아니라 인프라 상황이므로, 무한정 붙잡고 있기보다 **지수 백오프 재시도**로 시스템 차원에서 흡수하는 게 정석 대응

## [3] MCP 서버가 두 번째 클라이언트부터 "Already connected to a transport"로 죽음

- **프로젝트**: payment-aiops-platform — MCP 서버 (TypeScript)
- **기술 태그**: MCP SDK, Streamable HTTP, Node.js
- **날짜/시기**: 2026-09-23

### 1. 상황
Phase 4에서 만든 MCP 서버를 `curl`로 테스트할 땐 정상 동작을 확인했음. 이후 이 서버를 `.mcp.json`에 등록해 Claude Code(이 세션)에서 실제로 연결해보려 함.

### 2. 문제
Claude Code가 연결을 시도하자 500 에러: `Error: Already connected to a transport. Call close() before connecting to a new transport.`

### 3. 원인 분석 과정
`curl` 테스트 때는 세션을 하나만 만들고 끝냈어서 문제가 안 드러났었음. 코드를 다시 보니 `McpServer` 인스턴스를 모듈 최상단에 **딱 하나만** 만들어서 모든 요청 핸들러가 공유하고 있었고, 새 세션(initialize 요청)이 들어올 때마다 그 하나뿐인 `server` 인스턴스에 `server.connect(새_transport)`를 호출하고 있었음. `McpServer.connect()`는 한 번 호출되면 그 인스턴스를 해당 transport에 영구히 묶어버리는 API라, 두 번째 클라이언트(Claude Code)가 접속하면서 이미 하나의 transport에 연결된 서버를 또 connect()하려다 에러가 난 것.

### 4. 시도했던 것들
- (확인) 에러 메시지를 그대로 검색하지 않고, "이전에 됐던 걸 왜 지금 안 되지"를 먼저 따짐 - curl 테스트는 매번 새 프로세스/세션 하나로 끝냈지만, 이번엔 "두 번째 연결"이 처음 발생한 상황이라는 차이를 포착
- (성공) 도구 등록 로직을 `createServer()` 팩토리 함수로 빼서, 세션(연결)마다 새 `McpServer` 인스턴스를 만들도록 수정. `transports` 맵은 그대로 세션ID→transport 매핑을 유지

### 5. 최종 해결 방법
`app.post("/mcp", ...)`의 initialize 분기에서 `createServer()`로 매번 새 `McpServer`를 만들고, 그 새 인스턴스에만 `connect()`를 호출하도록 변경. curl로 세션 2개를 동시에 열어 둘 다 200으로 정상 초기화되는 것을 확인.

### 6. 결과
Claude Code를 포함해 여러 클라이언트가 각자 독립된 세션으로 동시에 이 MCP 서버에 붙을 수 있게 됨 (나뿐 아니라 나중에 Phase 8의 Python 에이전트도 동시에 연결될 예정이라 반드시 필요한 수정이었음).

### 7. 배운 점
- **"전에 테스트했을 때 됐다"는 "지금 상황에서도 된다"를 보장하지 않는다.** 테스트 시나리오(단일 세션)와 실제 사용 시나리오(다중 세션)가 다르면, 단일 세션 테스트만으로는 절대 못 잡는 버그가 있다 - 처음부터 "이 서버에 클라이언트가 여러 개 붙을 수 있나?"를 테스트 케이스에 넣었어야 함
- 상태를 가진 객체(McpServer)를 요청 핸들러 바깥의 모듈 전역에 두면, "요청마다 독립적이어야 하는 것"과 "정말 공유해도 되는 것"을 구분하지 못하고 실수하기 쉽다

## [2] 분산 트레이싱(OTel+Tempo) 구축 - 3중으로 겹친 문제를 하나씩 벗겨낸 사례

- **프로젝트**: payment-aiops-platform — payment-api + db-writer-consumer (Java/Spring Boot)
- **기술 태그**: OpenTelemetry, Micrometer Tracing, Grafana Tempo, Spring Boot 4.x, Docker
- **날짜/시기**: 2026-09-23

### 1. 상황
MSA 구조를 보강하면서 분산 트레이싱을 추가하기로 함. `management.tracing.sampling.probability`, `management.otlp.tracing.endpoint` 두 프로퍼티만 설정하면 Spring Boot가 알아서 OpenTelemetry로 trace를 Tempo에 보내줄 거라 예상하고 시작함 (Spring Boot 3.x 문서에서 익숙했던 방식).

### 2. 문제
프로퍼티를 설정하고 요청을 보내도 Tempo에 trace가 전혀 쌓이지 않음. 에러 로그조차 없이 조용히 아무 일도 안 일어남 - 디버깅 난이도가 가장 높은 유형("에러가 없는데 안 됨").

### 3. 원인 분석 과정 (세 겹의 문제였음)
**1단계 - Spring Boot가 아예 트레이싱을 시도하지 않음**: `--debug` 플래그로 자동설정 조건평가 리포트를 보려다 CLI 인자 전달에서 막혀서, 대신 `logging.level.root: DEBUG`로 전체 로그를 열어 재현 요청을 보내봄. 그런데 "tracing"이나 "otlp" 관련 로그가 자동설정 후보 목록에 아예 등장하지 않음 - "조건에 안 맞아서 안 됨"이 아니라 "그런 자동설정 클래스 자체가 없음"이라는 뜻으로 해석하고, `spring-boot-actuator-autoconfigure-4.1.1.jar`를 `jar tf`로 열어 내용물을 확인함. 실제로 `tracing`, `otlp`, `zipkin` 관련 클래스가 단 하나도 없었음 - 이 Spring Boot 버전(4.1.1)에서 트레이싱 자동설정 모듈이 완전히 빠져있거나 다른 곳으로 재구성된 것으로 결론.

**2단계 - 수동 배선 후에도 export가 실패함**: Spring Boot 자동설정에 의존하지 않고 OpenTelemetry SDK(`SdkTracerProvider`, `OtlpHttpSpanExporter`)와 Micrometer Tracing 브릿지(`OtelTracer`, `OtelPropagator`, `OtelCurrentTraceContext`)를 `@Bean`으로 등록하고, `ObservationRegistryCustomizer`로 tracing handler를 연결함(패키지 경로가 `org.springframework.boot.micrometer.observation.autoconfigure`로 바뀐 것도 jar 내부를 뒤져서 알아냄). 컴파일은 성공했지만 실행하니 `Failed to export spans: unexpected end of stream` 에러 발생.

**3단계 - "unexpected end of stream"의 진짜 원인**: 처음엔 `localhost`가 Windows에서 IPv6(`::1`)로 먼저 풀리는데, 마침 WSL2의 `wslrelay.exe`가 같은 포트(4318)를 점유하고 있어서 충돌하는 거라 의심함 (`Get-NetTCPConnection`으로 실제로 두 프로세스가 같은 포트에 물려있는 걸 확인). `127.0.0.1`로 바꿔서 재시도했지만 동일하게 실패 - 가설이 틀렸다는 뜻. 같은 Docker 네트워크 안에 임시 `curl` 컨테이너를 띄워 `tempo:4318`로 요청해보니 호스트 경유 여부와 무관하게 **"Connection refused"** - 즉 Tempo 컨테이너 "안"에서부터 이미 문제였음. `docker logs`로 Tempo 자체 시작 로그를 다시 보니 `Starting HTTP server ... endpoint=127.0.0.1:4318` - Tempo의 OTLP 리시버가 `tempo.yaml`에 주소를 명시하지 않으면 기본값으로 컨테이너 "자기 자신의 루프백(127.0.0.1)"에만 바인딩된다는 걸 발견함. 이러면 다른 컨테이너는 물론 호스트의 포트포워딩(`4318:4318`)으로도 절대 도달할 수 없다.

### 4. 시도했던 것들
- (실패) `management.tracing.*`/`management.otlp.tracing.*` 프로퍼티 설정 → 자동설정 클래스 자체가 없어서 무효
- (확인) `jar tf`로 actuator-autoconfigure jar 내부 열람 → 트레이싱 관련 클래스 부재 확인
- (성공) OpenTelemetry SDK + Micrometer Tracing을 `@Bean`으로 수동 배선
- (실패) `localhost:4318` → WSL2 wslrelay 충돌 의심, `127.0.0.1:4318`로 변경 → 여전히 실패 (가설 기각)
- (확인) 같은 Docker 네트워크의 임시 curl 컨테이너로 `tempo:4318` 호출 → "Connection refused"로 범위를 Tempo 컨테이너 내부로 좁힘
- (성공) `tempo.yaml`의 OTLP 리시버에 `endpoint: 0.0.0.0:4318`/`0.0.0.0:4317` 명시 → 문제 해결

### 5. 최종 해결 방법
- `payment-api`/`db-writer-consumer` 각각에 `TracingConfig.java`를 만들어 OTel SDK + Micrometer Tracing을 수동으로 배선 (Spring Boot 자동설정에 의존하지 않음)
- `observability/tempo.yaml`의 OTLP 리시버에 `http`/`grpc` 모두 `0.0.0.0` 바인딩을 명시

### 6. 결과
`http post /payments` 요청 하나를 보낸 뒤 Tempo에서 trace를 조회하니, **payment-api의 HTTP 요청 span + Kafka 발행(producer) span, 그리고 db-writer-consumer의 Kafka 수신(consumer) span까지 전부 하나의 trace ID로 이어져 있는 것**을 확인함 (`serviceStats: {"payment-api": 2 spans, "db-writer-consumer": 4 spans}`). 서로 다른 프로세스, 다른 서비스가 Kafka 메시지 헤더를 통해 trace context를 주고받아 하나의 요청 흐름으로 재구성된 것을 눈으로 확인한 셈.

### 7. 배운 점
- **"에러 로그가 없다"는 "동작하고 있다"를 의미하지 않는다.** 자동설정이 아예 시도조차 안 하는 경우, 에러 대신 그냥 침묵함 - 이럴 땐 "왜 실패했나"가 아니라 "애초에 시도는 하고 있나"부터 확인해야 함
- 새 프레임워크 버전에서 뭔가 안 되면, 문서를 찾기 전에 **실제 jar 안에 그 클래스가 있는지부터 확인**하는 게 가장 빠른 경우가 있다 (특히 아직 문서화가 부족한 최신 버전일 때)
- **원인을 하나 고쳤다고 안심하면 안 된다.** 이번 문제는 원인이 3개 겹쳐 있었고, 1개를 고치고도 증상이 똑같아서 "가설이 틀렸다"를 인정하고 범위를 다시 좁혀야 했음. 이때 "같은 네트워크 안의 임시 컨테이너로 테스트"처럼 변수를 하나씩 제거해 나가는 접근이 결정적이었음
- 컨테이너화된 서비스의 기본 바인딩 주소(0.0.0.0 vs 127.0.0.1)는 항상 명시적으로 확인해야 하는 값이다 - "포트를 열었다"와 "외부에서 접근 가능하다"는 다른 얘기

## [1] Spring Kafka JsonSerializer가 기본 설정으로는 못 쓰는 상태였음 (Jackson 누락 + epoch 타임스탬프)

- **프로젝트**: payment-aiops-platform — 결제 API (Java/Spring Boot)
- **기술 태그**: Spring Boot 4.x, Spring Kafka, Jackson, JSR-310
- **날짜/시기**: 2026-09-23

### 1. 상황
Phase 1(결제 API)에서 `POST /payments`가 요청을 받아 Kafka로 발행하는 기능을 구현하고 첫 테스트를 하는 중이었음. `spring-boot-starter-webmvc` + `spring-boot-starter-kafka` 의존성만 있으면 JSON 직렬화가 당연히 될 거라고 예상함.

### 2. 문제
1차: `POST /payments` 호출 시 500 에러. 서버 로그에 `KafkaException: Failed to construct kafka producer` -> 원인은 `ClassNotFoundException: com.fasterxml.jackson.databind.JavaType`.
2차(1차 해결 후): 다시 500 에러. 이번엔 `InvalidDefinitionException: Java 8 date/time type java.time.Instant not supported by default`.
3차(2차 해결 후): 200/202는 나오는데, Kafka에 쌓인 메시지를 확인해보니 `requestedAt` 필드가 `"2026-09-22T22:27:01Z"` 같은 문자열이 아니라 `1790116102.2914807` 같은 epoch 숫자로 나가고 있었음.

### 3. 원인 분석 과정
1. 1차 에러는 스택트레이스 root cause를 보고 바로 "Jackson이 클래스패스에 없다"는 걸 확인. `mvnw dependency:tree | Select-String jackson`으로 실제로 jackson 관련 의존성이 트리에 단 하나도 없다는 걸 확인함 - 예전 Spring Boot(3.x 이하)에서는 `spring-boot-starter-web`이 `spring-boot-starter-json`을 통해 Jackson을 자동으로 끌고 왔는데, 이번에 쓴 Spring Boot 버전의 `spring-boot-starter-webmvc`는 그렇지 않다는 걸 실제로 겪으며 확인.
2. `jackson-databind`를 추가해 1차는 해결됐지만 2차 에러 발생. 에러 메시지 자체가 "jackson-datatype-jsr310 모듈을 추가하라"고 정확히 알려줘서 바로 원인 특정.
3. 3차(epoch 문제)는 에러가 아니라 "동작은 하는데 출력 포맷이 이상한" 케이스라 더 까다로웠음. Kafka 토픽을 `kafka-console-consumer.sh`로 열어보고 나서야 발견함 - API 응답(202)만 보고 넘어갔으면 놓쳤을 문제. Spring Kafka의 `JsonSerializer`가 `spring.kafka.producer.value-serializer` 프로퍼티만으로 설정될 때는 Spring이 관리하는 공용 `ObjectMapper`가 아니라 Spring Kafka 자체의 기본 `ObjectMapper`(`JacksonUtils.enhancedObjectMapper()`)를 쓰고, 이 기본값이 `SerializationFeature.WRITE_DATES_AS_TIMESTAMPS=true`라는 걸 문서에서 확인.

### 4. 시도했던 것들
- (해결) `jackson-databind` 의존성 추가 -> 1차 에러 해결
- (해결) `jackson-datatype-jsr310` 의존성 추가 -> 2차 에러 해결
- (시도, 실패) `KafkaProperties` 빈을 주입받아 `buildProducerProperties()`로 설정을 만들려 했으나, 이번 Spring Boot 버전에서는 `org.springframework.boot.autoconfigure.kafka.KafkaProperties` 클래스 자체를 찾을 수 없어서 컴파일 실패
- (최종 해결) `@Value`로 `bootstrap-servers`/`acks`를 주입받아 `Map.of(...)`로 최소한의 producer 설정을 구성하고, `JsonSerializer`에 `WRITE_DATES_AS_TIMESTAMPS`를 끈 커스텀 `ObjectMapper`를 명시적으로 넣어주는 `ProducerFactory`/`KafkaTemplate` 빈을 정의

### 5. 최종 해결 방법
`KafkaProducerConfig.java`에서 커스텀 `ObjectMapper`(`JavaTimeModule` 등록 + `WRITE_DATES_AS_TIMESTAMPS` 비활성화)를 만들고, 이를 사용하는 `JsonSerializer`로 `ProducerFactory`/`KafkaTemplate`을 Bean으로 등록함. `application.yml`의 `spring.kafka.producer.key/value-serializer` 설정은 이제 이 커스텀 Bean에 의해 무시되므로 제거하고 그 이유를 주석으로 남김.

### 6. 결과
`kafka-console-consumer.sh`로 실제 메시지를 열어 `requestedAt`이 `"2026-09-22T22:31:01.494671300Z"` 형태의 ISO-8601 문자열로 나가는 것을 확인. 나중에 Python(이상탐지 에이전트)이나 TypeScript(게이트웨이) 쪽에서 이 필드를 파싱할 때 언어별 epoch 처리 방식 차이로 혼선이 생기는 걸 미리 방지함.

### 7. 배운 점
- **프레임워크 버전이 바뀌면 "당연히 될 거라 생각했던 것"이 안 될 수 있다.** Spring Boot 3.x에서 익숙했던 "web 스타터 = Jackson 자동 포함" 가정이 이 버전에서는 깨졌음 - 새 버전을 쓸 때는 익숙한 스타터라도 실제 의존성 트리를 한 번 확인하는 습관이 필요함
- **"응답 코드가 정상(202)"이라고 끝난 게 아니다.** epoch 타임스탬프 문제는 API 레벨에서는 전혀 티가 안 났고, Kafka 토픽을 열어봐야만 발견할 수 있었음 - 프로듀서를 만들었으면 그 프로듀서가 실제로 무엇을 내보내는지 소비자 관점에서 확인하는 습관이 중요함
- Spring Kafka에서 `value-serializer`를 문자열 클래스명으로 설정하는 방식은 커스터마이징 여지가 없다는 것도 이번에 확인 - 직렬화 방식을 세밀하게 제어하려면 처음부터 `ProducerFactory`/`KafkaTemplate`을 Bean으로 정의하는 게 낫다
